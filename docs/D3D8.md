# Direct3D 8 research

Status: **translation routes identified; local comparison pending**.

Direct3D 8 deserves its own adapter decision instead of being treated as merely “old D3D9”. Three routes are currently worth testing.

## Route A — native D3D8 interception

A `d3d8.dll` proxy can observe the original API before any translation. This maximizes access to D3D8 transforms, shader bytecode, render-target/depth state and draw calls that may later help reconstruct motion vectors or projection jitter.

The cost is that all modern-resource transport remains unsolved at this layer. The likely useful output of a native adapter is therefore renderer semantics plus selected payloads, not an attempt to make D3D8 resources directly consumable by a modern backend.

## Route B — d3d8to9 -> D3D9

`crosire/d3d8to9` is a pseudo-driver that converts D3D8 API calls and low-level shaders to equivalent D3D9 operations. ReShade's current setup detects D3D8 applications and explicitly directs users to this wrapper before installing the D3D9 ReShade path.

Advantages:

- narrow translation boundary: D3D8 semantics are mapped only as far as D3D9;
- open source, BSD-2-Clause;
- allows reuse of whatever D3D9 adapter/relay LTR Bridge eventually proves;
- mature enough to be the path ReShade itself recommends for D3D8.

Limitations:

- it is still translation, so behavior can differ from native D3D8 on modern Windows/drivers;
- it outputs ordinary D3D9, so it does not remove the classic-D3D9 versus D3D9Ex sharing question;
- information may already have been transformed before an LTR Bridge D3D9 adapter sees it.

There is a small third-party `d3d8to9ex` fork that targets D3D9Ex, but its existence is only research evidence. It must not be treated as a production dependency or proof that D3D8 can universally take the D3D9Ex sharing path.

## Route C — dgVoodoo2 -> D3D11/D3D12

dgVoodoo2 implements D3D8 and D3D9 over modern D3D11/12 and can make downstream tooling see a modern renderer immediately.

Potential benefit: maximum reuse of the D3D11/D3D12 side of LTR Bridge.

Potential costs: a larger translation boundary, less visibility into the original D3D8 renderer semantics, proxy/injector coexistence concerns, and redistribution restrictions that prevent treating dgVoodoo2 as a generic built-in framework component.

## Proposed experiment

Use one controlled D3D8 scene and capture the same cases through:

1. native D3D8 interception;
2. d3d8to9 followed by the chosen D3D9 path;
3. dgVoodoo2 followed by the D3D11 path.

Compare image correctness, depth availability, transform/shader visibility, resource-copy count, frame pacing, reset/fullscreen behavior, and proxy/mod coexistence. Do not choose a default D3D8 route before this comparison.

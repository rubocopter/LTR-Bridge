# Direct3D 9 research

Status: **current-host D3D9Ex local render target -> shared relay -> private D3D11 conversion -> existing x86/x64 D3D12 transport implemented and host-tested; controlled interception and real Call of Juarez observation are host-tested; the replacement multiframe transport is connected to the observer and compile-tested, while its real-game and reset-generation behavior remain experiment-pending**.

## Newly identified D3D9 -> D3D11 relay candidate

Microsoft's `ID3D11Device::OpenSharedResource` documentation explicitly describes a texture created by a Direct3D 9 device with `CreateTexture(..., pSharedHandle)` being opened by a D3D11 device. This makes a private D3D11 relay a concrete candidate without translating the whole game renderer.

The documented D3D9 -> D3D11 texture restrictions are significant:

- 2D texture, one mip level;
- default usage and write-only from the D3D9 side;
- no MSAA;
- resource must be usable as shader resource and render target on the D3D11 side;
- only `R10G10B10A2_UNORM`, `R16G16B16A16_FLOAT`, and `R8G8B8A8_UNORM` are documented for this interop path.

Those restrictions mean native game depth surfaces generally cannot simply be exported as-is. A direct adapter may need to copy or encode color, depth and motion-vector payloads into dedicated relay textures. `R16G16B16A16_FLOAT` is potentially useful for reconstructed depth/MV payloads, but that is a hypothesis until tested.

## D3D9 vs D3D9Ex ambiguity

There is an important primary-documentation inconsistency to resolve experimentally. `ID3D11Device::OpenSharedResource` describes a Direct3D 9 -> D3D11 path generically, while Microsoft's broader surface-sharing overview says unsynchronized surface sharing is supported by the Direct3D 9Ex runtime and that Direct3D 9c and older runtimes do not support shared surfaces.

Do not treat the relay route as available to every classic D3D9 game until a controlled probe establishes exactly which device/runtime combinations work.

## Local interop probe

**Implemented/host-tested:** `src/d3d9_d3d11_share_probe/` builds as a Win32 executable and creates equivalent classic `IDirect3D9` and `IDirect3D9Ex` devices on the same NVIDIA adapter used by the D3D11 consumer (`vendor=0x10de`, `device=0x2782` on the current host). Each successful D3D9Ex case creates a local render-target texture plus a dedicated shared relay in `D3DPOOL_DEFAULT`, copies renderer output into the relay with `StretchRect`, synchronizes with a `D3DQUERYTYPE_EVENT`/`D3DGETDATA_FLUSH` completion point, opens the relay through `ID3D11Device::OpenSharedResource`, copies only to a staging texture for validation, and checks pixel contents. The probe also executes `ResetEx` and recreates resources from `64x64` to `96x72` mid-case.

**Host-tested classic D3D9 result:** all four attempted shared-texture cases return `D3DERR_INVALIDCALL` (`0x8876086c`) from `IDirect3DDevice9::CreateTexture(..., pSharedHandle)` before a shared handle exists. This was reproduced in five additional runs. It is strong evidence against assuming the documented relay works through the classic runtime on this host, but it is not a universal Windows/driver result.

**Host-tested cross-runtime result:** the probe also creates shared R10, RGBA16F and BGRA8-control textures successfully on D3D9Ex and passes each resulting handle to a classic D3D9 `CreateTexture(..., pSharedHandle)` open attempt. The classic device opens `0/3`; every attempt returns `D3DERR_INVALIDCALL` (`0x8876086c`). This closes the simple inverse-relay hypothesis on the current host: keeping the game on classic D3D9 while a helper creates the shareable D3D9Ex resource does not provide the missing transport boundary here.

**Host-tested D3D9Ex result:** `D3DFMT_A2B10G10R10 -> DXGI_FORMAT_R10G10B10A2_UNORM` and `D3DFMT_A16B16G16R16F -> DXGI_FORMAT_R16G16B16A16_FLOAT` both create shared handles and open in D3D11 with `BindFlags=0x28` (`RENDER_TARGET | SHADER_RESOURCE`). The probe now drives those relays from a real local D3D9Ex render target via `StretchRect`, uses `D3DQUERYTYPE_EVENT` for completion, performs one `ResetEx`, recreates the relay at `64x64 -> 96x72`, and completes 12 frames with zero mismatches. Five additional runs reproduced the same result. The documented `D3DFMT_A8B8G8R8 -> DXGI_FORMAT_R8G8B8A8_UNORM` case returns `D3DERR_INVALIDCALL` on this host.

**Observed host-specific control:** ordinary D3D9 `D3DFMT_A8R8G8B8` is outside the documented D3D9 -> D3D11 format list, yet D3D9Ex on this host creates and shares it successfully as `DXGI_FORMAT_B8G8R8A8_UNORM`; the same two-generation/12-frame validation passes in all five repetitions with `BindFlags=0x28`. Treat this as driver/runtime evidence only, not a portable relay contract.

The explicit synchronization used here is CPU-observed completion, not a shared GPU fence: D3D9 completes `StretchRect` through an event query before D3D11 touches the resource. Across five repeated independent-probe runs, the per-frame CPU wall interval for `StretchRect + event-query completion` averaged about `0.262 ms` for R10, `0.237 ms` for RGBA16F and `0.240 ms` for the BGRA8 control. These values include synchronization and are not `performance-validated` relay latency numbers.

**Implemented/host-tested end-to-end route:** the x86 bridge producer creates a same-adapter D3D9Ex device and local `A2B10G10R10` render target, binds that target, clears it through normal D3D9Ex render-target state, restores the default target, copies into a shareable R10 relay, waits for the D3D9 event query, opens the relay in a private x86 D3D11 device, and runs a fullscreen shader into the existing host-created shared `R8G8B8A8_UNORM` transport resource. The established ready/done fence protocol then carries the frame into the x64 D3D12 consumer, which performs its existing compute transform before x86 validation. At the generation boundary, `ResetEx` succeeds and both the relay and modern transport resources are recreated. Five dedicated 24-frame repetitions pass for the original `64x64 -> 96x72` profile and five more pass for `1920x1080 -> 2560x1440`, all with zero mismatches. Validation explicitly uses `rgb8_plus_minus_1_lsb` because D3D9 render-target quantization can differ from the synthetic 8-bit reference by one LSB. Across current-implementation run means, the tiny profile averages about `0.2647 ms` for D3D9Ex bind/clear/restore/`StretchRect`/event completion plus `1.9701 us` for the D3D11 R10-relay-to-RGBA8 shader; the high-resolution profile averages about `0.3637 ms` and `19.5638 us`. These controlled single-host measurements are transport evidence only, not performance validation.

**Implemented/host-tested controlled scene:** `src/d3d9ex_scene_probe/` moves beyond color fills without becoming an injector. It creates engine-owned R10 color, D24S8 depth and default-pool vertex-buffer resources, renders overlapping near/far triangles with fixed-function world/view/projection state, and validates that depth rejects the later far triangle in the overlap. At the capture point the engine color target and depth surface are still bound and `GetTransform(D3DTS_WORLD)` returns the per-frame world transform. `StretchRect` from that still-bound color target into the shared R10 relay succeeds, then D3D11 readback validates clear, red-only, red-over-green overlap and green-only samples. The probe recreates resources after one `ResetEx` from `640x360` to `1280x720`. Five repeated runs pass with zero mismatches; their `StretchRect + event` CPU-wall run means are `0.3659–0.3906 ms` (about `0.3786 ms` overall). The corresponding `--d3d9ex-scene-relay` bridge mode carries the same scene through private D3D11 conversion and the x64 D3D12 compute path. Five 24-frame runs pass with zero mismatches, one reset and one generation transition; their scene-draw/capture CPU-wall means are `0.2743–0.2954 ms` (about `0.2881 ms` overall) and D3D11 relay-to-RGBA8 shader means are `4.9333–5.1507 us` (about `5.0509 us`). Scene-path output validation permits ±2 RGB8 LSB after R10 quantization/conversion. These numbers are short single-host probe measurements, not performance validation.

**Implemented/host-tested external interception boundary:** `src/d3d9ex_intercept_probe/` splits the renderer and capture code into a Win32 target executable and a separate interceptor DLL. The target cooperatively loads the DLL before creating D3D9Ex, but does not pass renderer devices, surfaces, transforms or frame callbacks to it. The interceptor patches the executable's `Direct3DCreate9Ex` IAT entry and then the returned COM vtables for `CreateDeviceEx`, `EndScene` and `ResetEx`. After each real `EndScene`, it discovers the current render target, D24S8 depth surface and world transform from the device, creates its own shareable R10 relay, performs `StretchRect + D3DQUERYTYPE_EVENT`, opens the relay in a private same-adapter D3D11 device and validates the same clear/red/overlap/green samples. It re-reads render target, depth and world transform after capture and rejects any state change. One intercepted `ResetEx` releases and recreates capture resources between `640x360` and `1280x720`. Five repeated 12-frame runs pass with zero mismatches, state preservation and clean process shutdown. Their `StretchRect + event` run means are `0.1903–0.2041 ms`, averaging about `0.1990 ms`. This proves a controlled API interception boundary in a separate executable; cooperative DLL loading, a synthetic target and local pixel readback mean it is still not a production injector or real-game integration.

## Real Call of Juarez observation

**Host-tested/observed:** the clean official Steam Call of Juarez build is a PE32/x86 classic-D3D9 renderer. It loads the system `d3d9.dll`, resolves `Direct3DCreate9`, creates `IDirect3D9`/`IDirect3DDevice9`, and does not create D3D9Ex in the observed startup path. A local `d3d9.dll` beside the game is ignored on this installation, so the reproducible observer uses an existing `ChromeEngine3.dll` dependency instead: a temporary pure-forwarder `d3dx9_29.dll` forwards the engine's imported functions to a copied real runtime while routing `D3DXGetShaderVersion` through `ltr_d3d9_real_observer_bootstrap.dll`. The bootstrap installs observation hooks and the runner removes all staged DLLs after the process exits, checking hashes before cleanup.

The real renderer reached `Present` with one observed device/swapchain at `2560x1440`. The first sample reported an `A8R8G8B8` render target (`D3DFMT` value `21`), a `D24X8` depth surface (`77`), no MSAA, and transform state visible at the same boundary. This establishes `Present` as a useful real-game observation point for the current build. It does not yet identify a complete temporal input set, distinguish scene color from every post/HUD pass, or provide a GPU transport path out of classic D3D9.

### D3D9Ex compatibility substitution

**Host-tested synthetic result:** an object created with `Direct3DCreate9Ex` can be exposed to legacy code through its base `IDirect3D9` interface. Calling the inherited `IDirect3D9::CreateDevice` on that object produced a device whose `QueryInterface(IDirect3DDevice9Ex)` succeeds. In the existing interop probe, that base-interface path shares the same R10, RGBA16F and BGRA8-control textures as the explicit `CreateDeviceEx` path, survives one reset/recreation per format, and completes 12 frames per format with zero mismatches.

**Host-tested real-game result:** the Call of Juarez observer can opt into the same substitution at the intercepted `Direct3DCreate9` call. The game continues through its normal D3D9 API, but the returned root is backed by D3D9Ex; its `2560x1440` fullscreen device reports `device_ex=1` and still reaches the same `Present` observation boundary. With the one-shot relay experiment enabled before `Present`, the observer creates a shared A8R8G8B8 texture at the real frame extent, copies the current game render target into it with `StretchRect`, completes the copy with a D3D9 event query, opens the shared handle in an x86 D3D11 device, and performs validation-only readback on both sides. Five sampled pixels match exactly (`sample_mismatches=0`).

**Host-tested one-shot x86/x64 result:** the same x86 D3D11 device then copies the opened game relay into a `DXGI_FORMAT_B8G8R8A8_UNORM` texture created with `D3D11_RESOURCE_MISC_SHARED_NTHANDLE | D3D11_RESOURCE_MISC_SHARED_KEYEDMUTEX`. After a D3D11 event-query completion point, `IDXGIResource1::CreateSharedHandle` produces an inheritable NT handle. A minimal x64 helper opens that exact resource with D3D12, copies it to a readback buffer and validates the same five points with zero mismatches. The observed D3D12 format is `87` (`B8G8R8A8_UNORM`). An initial attempt using `SHARED_NTHANDLE` alone returned `E_INVALIDARG`; the documented NT-sharing flag combination resolved the failure. This proves the exact real-game color resource can cross the x86/x64 boundary on the current host. The helper is deliberately synchronous and validation-heavy, so this is transport evidence rather than a production frame loop or performance result. Reset/device-loss behavior and broader gameplay compatibility of the D3D9Ex substitution remain pending.

**Observed failed real-game multiframe result / host-tested offline replacement:** the first persistent x64 experiment allocated a two-slot ring and shared ready/done fences for 12 real frames. Initialization succeeded in the game process, but the x64 sink timed out at completion and no multiframe PASS was produced. The experiment originally used D3D11-owned `SHARED_NTHANDLE | SHARED_KEYEDMUTEX` BGRA8 slots. A dedicated game-free reproduction later showed why that design should not be promoted on this host: ready/done fences could advance through all 12 values while D3D12 read back zero from all 12 slot copies, even after x86 switched from direct upload to local-texture `CopyResource` before `ready`. This is an observed current-host failure of that persistent ownership design, not a universal API prohibition.

The replacement `src/d3d9_real_bridge_probe/` follows the ownership direction already proven by the general x86/x64 bridge. The x64 D3D12 sink creates two shared `B8G8R8A8_UNORM` resources with `D3D12_HEAP_FLAG_SHARED` and simultaneous-access capability plus a shared `done` fence, duplicates the resource/fence handles directly into x86, and sends a compact bootstrap record through an inherited pipe. The shared x86 client opens those resources with `OpenSharedResource1`, opens `done` with `OpenSharedFence`, owns a named `ready` fence, copies a local texture into each slot, and checks both `done` and child liveness before reuse. After extracting the common client, five independent `64x64` and three `2560x1440` 12-frame runs pass with zero content mismatches and forced backpressure.

**Implemented/compile-tested observer join:** the real observer now uses that exact client behind `LTR_D3D9_TEST_MULTIFRAME`. At `Present`, it lazily creates two D3D9 shared relays matching the transport ring depth plus one reusable D3D9 event query, opens both relays in private D3D11, checks transport availability before copying, and sends the completed relay texture into the corresponding x64-owned slot. Source reuse no longer needs a second CPU-observed D3D11 event query: `done[n]` can only complete after the D3D12 queue has waited for `ready[n]`, and `ready[n]` is signaled after the D3D11 `CopyResource` that reads relay slot `n % 2`. Reusing the same relay only after the client admits that transport slot therefore preserves the required ordering while removing one per-frame D3D11 query/flush/spin wait. The x64 sink now performs a real GPU `CopyResource` from every shared slot into a private D3D12 consumer texture before signaling the matching `done`, so a passing live run proves actual D3D12 consumption rather than fence progression alone. The synthetic validator reads back from that consumer copy; after this change 3/3 forced-backpressure runs at `64x64` and 2/2 at `2560x1440` completed 12/12 frames with zero mismatches. Backpressure skips the capture rather than blocking the renderer. Transport errors disable the experiment and leave the original `Present` path active. `Reset` tears down the child and all default-pool resources before calling the game reset; a successful reset clears the observed resource-state sample, increments the resource generation and allows lazy reconstruction. The runner verifies color, depth and transforms on the current generation. Its optional `-RequireResetGeneration` mode deliberately stalls the generation-1 x64 consumer (configurable with `-ResetBridgeStallMs`) so a user-triggered game reset can exercise active bridge teardown; it then requires a fresh post-reset state sample plus matching observer/client/x64 completion for the new generation. The observer and runner compile/parse successfully, but that reset mode remains **experiment-pending** until executed in Call of Juarez.

**Implemented/host-tested dgVoodoo2 comparison:** the same target is exercised with official dgVoodoo2 `2.87.5` (2026-09-15). The native R10 profile fails before capture because dgVoodoo rejects the target render-texture creation with `D3DERR_INVALIDCALL`. The opt-in BGRA8 profile is valid under native D3D9Ex and renders through dgVoodoo, but the interceptor then receives `D3DERR_INVALIDCALL` when it tries to create the shared D3D9Ex relay. That proves the native D3D9Ex -> shared texture -> private D3D11 design does not traverse this wrapper/backend unchanged on the current host. A separate `src/dgvoodoo_addon_probe/` DLL uses the external official API package instead and registers for the D3D12 root observer. With `OutputAPI=d3d12_fl11_0`, five repeated `--bgra8 --no-interceptor --present` runs observe API version `0x287`, a non-null D3D12 device, `640x360 -> 1280x720` swapchain recreation and 12 matched `PresentBegin`/`PresentEnd` callbacks with non-null source/destination textures. The observed source resources are `DXGI_FORMAT_R8G8B8A8_TYPELESS`; the drawing targets are `DXGI_FORMAT_R8G8B8A8_UNORM`. The probe only observes descriptors/lifecycle and returns `false` from the presentation hook, so it does not alter dgVoodoo resources or presentation behavior. The D3D12 callback is a translated presentation boundary; this experiment does not establish original D3D9 depth, transform or motion-vector visibility there.

## Architectures to compare

1. **Native D3D9 interception + dedicated transport.** Maximum visibility into original transforms, shaders and draw state; transport mechanism remains to be proven.
2. **Native D3D9/D3D9Ex interception + shared-texture D3D11 relay.** Preserve the original renderer while converting temporal payloads into the narrow set of D3D9/D3D11-shareable textures, then reuse the modern D3D11 transport.
3. **dgVoodoo2 translation -> modern backend observation.** The official D3D12 addon API now provides a host-tested presentation-resource boundary, but it is later than the native D3D9 `EndScene` state boundary and still needs real-game evidence for temporal-data recovery. Proxy/coexistence and redistribution constraints remain part of the stack.

The controlled-target comparison now covers both synthetic boundaries on this host, and Call of Juarez adds a real renderer/relay boundary. True classic-D3D9 sharing still fails in both tested directions, but the game can run its legacy API against an Ex-backed root/device and then share the real frame into D3D11. Native D3D9Ex interception preserves visibility of the bound color/depth/world state, and the observer now contains the compile-tested join to the host-tested modern transport. The next integration step is live lifecycle validation of that join. dgVoodoo2 2.87.5 remains a comparison route: it does not accept the D3D9Ex shared-relay design as-is, but its official D3D12 addon API exposes stable translated presentation resources across the same reset/generation pattern. Classic-D3D9 failure, runtime-substitution compatibility, BGRA8 behavior and all dgVoodoo results remain host/version scoped.

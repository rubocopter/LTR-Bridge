# Direct3D 9 research

Status: **minimal x86 classic-D3D9/D3D9Ex -> D3D11 sharing probe implemented and host-tested; D3D9Ex works on the current host for selected formats while classic D3D9 does not expose the shared-texture path**.

## Newly identified D3D9 -> D3D11 relay candidate

Microsoft's `ID3D11Device::OpenSharedResource` documentation explicitly describes a texture created by a Direct3D 9 device with `CreateTexture(..., pSharedHandle)` being opened by a D3D11 device. This makes a private D3D11 relay a concrete candidate without translating the whole game renderer.

The documented D3D9 -> D3D11 texture restrictions are significant:

- 2D texture, one mip level;
- default usage and write-only from the D3D9 side;
- no MSAA;
- resource must be usable as shader resource and render target on the D3D11 side;
- only `R10G10B10A2_UNORM`, `R16G16B16A16_FLOAT`, and `R8G8B8A8_UNORM` are documented for this interop path.

Those restrictions mean native game depth surfaces generally cannot simply be exported as-is. A direct adapter may need to copy or encode color, depth and motion-vector payloads into dedicated relay textures. `R16G16B16A16_FLOAT` is potentially useful for reconstructed depth/MV payloads, but that is a hypothesis until tested.

## D3D9 vs D3D9Ex ambiguity

There is an important primary-documentation inconsistency to resolve experimentally. `ID3D11Device::OpenSharedResource` describes a Direct3D 9 -> D3D11 path generically, while Microsoft's broader surface-sharing overview says unsynchronized surface sharing is supported by the Direct3D 9Ex runtime and that Direct3D 9c and older runtimes do not support shared surfaces.

Do not treat the relay route as available to every classic D3D9 game until a controlled probe establishes exactly which device/runtime combinations work.

## Local interop probe

**Implemented/host-tested:** `src/d3d9_d3d11_share_probe/` builds as a Win32 executable and creates equivalent classic `IDirect3D9` and `IDirect3D9Ex` devices on the same NVIDIA adapter used by the D3D11 consumer (`vendor=0x10de`, `device=0x2782` on the current host). Each successful shared texture is created in `D3DPOOL_DEFAULT`, updated from a system-memory D3D9 texture with `UpdateTexture`, synchronized with a `D3DQUERYTYPE_EVENT`/`D3DGETDATA_FLUSH` completion point, opened by `ID3D11Device::OpenSharedResource`, copied only to a staging texture for validation, and checked pixel-for-pixel. The probe also releases/recreates the resource from `64x64` to `96x72` mid-case.

**Host-tested classic D3D9 result:** all four attempted shared-texture cases return `D3DERR_INVALIDCALL` (`0x8876086c`) from `IDirect3DDevice9::CreateTexture(..., pSharedHandle)` before a shared handle exists. This was reproduced in five additional runs. It is strong evidence against assuming the documented relay works through the classic runtime on this host, but it is not a universal Windows/driver result.

**Host-tested D3D9Ex result:** `D3DFMT_A2B10G10R10 -> DXGI_FORMAT_R10G10B10A2_UNORM` and `D3DFMT_A16B16G16R16F -> DXGI_FORMAT_R16G16B16A16_FLOAT` both create shared handles, open in D3D11 with `BindFlags=0x28` (`RENDER_TARGET | SHADER_RESOURCE`), survive one `64x64 -> 96x72` recreation and complete 12 frames with zero mismatches. Five additional runs reproduced the same result. The documented `D3DFMT_A8B8G8R8 -> DXGI_FORMAT_R8G8B8A8_UNORM` case returns `D3DERR_INVALIDCALL` on this host.

**Observed host-specific control:** ordinary D3D9 `D3DFMT_A8R8G8B8` is outside the documented D3D9 -> D3D11 format list, yet D3D9Ex on this host creates and shares it successfully as `DXGI_FORMAT_B8G8R8A8_UNORM`; the same two-generation/12-frame validation passes in all five repetitions with `BindFlags=0x28`. Treat this as driver/runtime evidence only, not a portable relay contract.

The explicit synchronization used here is CPU-observed completion, not a shared GPU fence: D3D9 finishes the update through an event query before D3D11 touches the resource. Across five repeated runs, the per-frame CPU wall interval for `UpdateTexture + event-query completion` averaged `0.3553 ms` for R10, `0.3859 ms` for RGBA16F and `0.3962 ms` for the BGRA8 control. The validation-only D3D11 `CopyResource + Map` interval averaged `0.5109`, `0.4382` and `0.3982 ms` respectively. These timings include synchronization/readback effects and are not `performance-validated` relay latency numbers.

## Architectures to compare

1. **Native D3D9 interception + dedicated transport.** Maximum visibility into original transforms, shaders and draw state; transport mechanism remains to be proven.
2. **Native D3D9/D3D9Ex interception + shared-texture D3D11 relay.** Preserve the original renderer while converting temporal payloads into the narrow set of D3D9/D3D11-shareable textures, then reuse the modern D3D11 transport.
3. **dgVoodoo2 D3D9 -> D3D11.** Simplifies downstream access to a modern API but may transform/hide original D3D9 state and adds proxy/coexistence and redistribution constraints.

The minimal runtime boundary is now resolved on the current host. The next D3D9 experiment should move one step closer to a real renderer: copy from a local D3D9 render target into the proven D3D9Ex relay formats, exercise device reset/recreation, then feed the private D3D11 relay into the existing x86 -> x64 modern-host transport before comparing the direct route with dgVoodoo2.

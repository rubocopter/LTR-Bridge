## Findings

### 1. Source compatibility blocks the current real vertical route — P1

**Observed:** promoted startup creates an Ex device and reaches Present, then Chrome begins hitting legacy `D3DPOOL_MANAGED` allocations that D3D9Ex rejects with `D3DERR_INVALIDCALL`. The first observed case is `CreateTexture(16,16,0,0,D3DFMT_A8R8G8B8,MANAGED,...)`, followed by a null read at `ChromeEngine3.dll+0x23E3FD`. Later tracing established additional exact failures rather than one unresolved generic null path.

**Verified:** managed resources are invalid on D3D9Ex. DEFAULT also changes locking and reset semantics, so successful creation is insufficient evidence of compatibility. See [Microsoft D3DPOOL, last updated 2021-03-15](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3dpool) and [resource management, last updated 2021-01-06](https://learn.microsoft.com/en-us/windows/win32/direct3d9/managing-resources).

**Live-tested addendum (2026-09-30):** the later null returned by Chrome's constructor is now explained. Static disassembly of `ChromeEngine3.dll+0x22FDF0` shows its cache-miss path calling device vtable slot `0x68`, `IDirect3DDevice9::CreateVertexBuffer`, with `Pool=1` (`D3DPOOL_MANAGED`). A one-shot breakpoint immediately after the call at `+0x22FEC6` observed `EAX=0x8876086C` (`D3DERR_INVALIDCALL`). The routine therefore leaves its output pointer null, `+0x230500` returns null, and the caller later faults at `+0x22F262`. An exact DEFAULT retry for that 0x40000-byte vertex buffer subsequently succeeded and at least 16 Lock/Unlock operations returned `S_OK`. The next exact MANAGED index buffer (`0x20000` bytes, usage `0x8`, `D3DFMT_INDEX16`) also returned `0x8876086C`; its narrow DEFAULT retry was live-tested returning `S_OK` with a non-null buffer.

**Live-tested addendum (2026-09-30):** D3D9 rewrites the device vtable during Chrome's state-block setup. The four observed Begin/End callsite pairs are `+0x2345D3/+0x2345EB`, `+0x2348E6/+0x234900`, `+0x234973/+0x234990` and `+0x234B83/+0x234B9B`; a hardware watchpoint traced the write to `d3d9.dll+0x124128` (`rep movsd`). The observed canonical device table is `d3d9.dll+0x1008`, with slot 26 at `+0x1070`. A direct `IDirect3DDevice9::BeginStateBlock` hook is the current diagnostic mechanism; it restores the relevant observer/compatibility hooks after each refresh. A later live run recorded 22 successful `begin_state_block_rehook` events with `observer_hooks=1`. Reusable INT3/trap-flag breakpoint rearming regressed control flow and is not a production candidate.

**Live-tested / observed addendum (2026-09-30):** the fresh Ex experiment now proves `S_OK`/non-null from the exact 64x64 DXT1 DEFAULT retry after original `0x8876086C`. Hooks survive 37 BeginStateBlock refreshes and the tracked VB reaches 24 successful Lock/Unlock pairs. The next 1x1 A8R8G8B8 MANAGED texture (`levels=1`, usage=0) is rejected and Chrome faults at `+0x23E3FD`; sustained Ex startup still fails. The five narrow retries establish allocation success on this build/host only, not managed-resource semantics.

### 2. Removed-device fence sentinel is now rejected — P1 hardening closed for the probe

**Implemented / verified:** shared `fence_reached(completed, target)` now rejects `UINT64_MAX` before applying the ordinary `>= target` rule, and the sink rechecks the completed value after an event wakeup. The same helper is used by the client reuse/completion checks. D3D12 documents `UINT64_MAX` as the removed-device sentinel; see [Microsoft ID3D12Fence::GetCompletedValue, last updated 2024-02-22](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12fence-getcompletedvalue).

**Host-tested:** probe-only D3D12 removal produces `ready_completed=18446744073709551615`; the sentinel is rejected (`sentinel_rejected=1`), the sink exits nonzero and the producer does not report PASS. A separate parent-exit probe also establishes that parent liveness wins the failure classification when producer teardown turns the shared fence into the removed-device sentinel: the sink reports `reason=parent_exited` instead of misclassifying the event as a generic fence wait failure. This is controlled failure injection on the current host. Broader device-loss timing and the real observer's fail-open behavior remain **experiment-pending**.

### 3. Bootstrap handle ownership is explicit — P1 hardening closed for the tested paths

**Implemented / verified:** the sink tracks handles duplicated into the parent until bootstrap publication succeeds and closes those remote duplicates on partial duplication/publication failure. The client wraps all incoming bootstrap handles in RAII before opening resources/fences, so an early open/descriptor failure closes the remaining inventory. See [Microsoft DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle).

**Host-tested:** a fresh eight-repeat bootstrap-failure run reports process handle count `616 -> 616`, growth zero. Probe-only invalid resource and done-fence handles also reach the intended open failure paths without PASS. Additional resource channels should keep the same ownership model.

### 4. Submission backpressure now has a bounded diagnostic failure path — P2 hardening partially closed

**Implemented / host-tested:** the synthetic producer now has `--submission-timeout-ms` (default 10,000 ms). The deadline is reset after every successful submit; if backpressure prevents progress for the declared interval the client is cancelled, the producer returns exit 8, and completion is classified separately as `RESULT CANCELLED`. A 3-frame probe with a 5,000 ms sink stall and 100 ms submission budget reaches that cancellation path and terminates cleanly.

The D3D9 capture query uses 10,000 polling iterations plus `Sleep(0)` (`proxy.cpp:572`), not an elapsed-time budget. Capture failures return to Present but can repeat on later frames. **Experiment-pending:** actual stalls, fail-open latency and retry policy under resource/device failure. Use declared wall-time budgets for diagnostics and a supervised fault experiment.

**Host-tested lifecycle negatives:** an 11,000 ms producer pause after frame 2 resumes and completes a four-frame transport with ready/done=4 and zero sampled mismatches, so a temporary interframe gap longer than ten seconds is not treated as a sink timeout. Parent termination while the sink waits for `ready` is classified as `parent_exited`. Deterministic probe-only injections also reach the `signal_done` consumer-copy failure and final-completion failure branches. Together with invalid resource/fence opens and removed-device injection, the five-case fault verifier reports PASS. These checks establish bounded transport behavior only; real renderer consumer loss and fail-open presentation remain separate experiments.

**Verified:** the XeSS probe's final PASS does not require responsive MAE improvement or distinct outputs (`src/xess_native_aa_probe/probe.cpp:628`). Existing measured improvement remains historical host evidence; PASS alone is execution evidence.

### 6. Frame omission is not yet represented as temporal identity — P1 integration gate

**Verified:** observer backpressure skips game captures while transport numbering counts successful submissions. The bootstrap protocol is a color-slot/fence contract, not a complete temporal frame contract. `TemporalFrameDescription` has provisional frame/view/resource/history identity, but does not yet express camera/config identity, depth convention, valid subrects, frame delta or output ownership; `CanReuseHistory` relies on callers to manage generations correctly (`src/temporal/temporal_frame.h:73`).

**Experiment-pending:** synchronized real color/depth/matrices/MV and actual renderer jitter. `GetDepthStencilSurface` exposes a resource descriptor, not shader-readable depth; successful `GetTransform` does not prove the effective matrices used by shader draws. Pair inputs with the captured game's frame and view, distinguish game-frame gaps from transport serials, and reset or deliberately account for gaps. Never attach current color to stale previous-frame guidance silently.

# Direct3D 10 research

Status: legacy shared-resource relay and x86 -> x64 bridge integration implemented and host-tested on the current machine; temporal-data integration pending.

Current DLSS5-Feeder demonstrates a D3D10 path that copies game resources into legacy shared textures, opens them through a private D3D11 device on the same adapter, and then reuses its D3D11-to-x64-host path.

This is relevant because D3D10 does not expose the same NT-handle resource and shared-fence path used by D3D11/D3D12 interop.

Microsoft documents D3D10.1 shared-resource synchronization, while Feeder reports different behavior on tested hardware and uses another synchronization method. LTR Bridge must probe the actual result on each test configuration rather than assume one universal rule.

## Local relay evidence

**Implemented/host-tested:** the Win32 probe creates a D3D10.1 hardware device at feature level 10.0 and a private D3D11 device on the same adapter. For each generation it creates a local `R10G10B10A2_UNORM` engine render target plus a legacy `D3D10_RESOURCE_MISC_SHARED` R10 relay. D3D10 copies the engine target into the relay, waits for `D3D10_QUERY_EVENT`, and D3D11 opens the legacy handle and validates the resulting pixels. The probe recreates resources from `640x360` to `1280x720`. Five repeated runs completed 12 frames each with zero mismatches; their copy+event CPU-wall run means were `0.2026–0.2108 ms`, averaging about `0.2067 ms`.

**Implemented/host-tested:** the same D3D10 source path is integrated into the existing x86/x64 bridge. The private x86 D3D11 device opens the R10 relay, converts it with the existing fullscreen shader into the host-created shared RGBA8 transport, and the x64 D3D12 consumer follows the established compute/fence path. Five repeated 24-frame runs completed the `640x360 -> 1280x720` generation transition with zero mismatches. The D3D10 copy+event run means were `0.1832–0.1902 ms` (about `0.1866 ms` average) and the D3D11 R10-to-RGBA8 conversion means were `4.9053–5.2747 us` (about `5.0531 us` average). These are controlled single-host synthetic measurements, not performance validation.

**Observed on the current host:** creating the equivalent D3D10 keyed-mutex resource with `D3D10_RESOURCE_MISC_SHARED_KEYEDMUTEX` returns `E_INVALIDARG` (`0x80070057`) on the RTX 4070 Ti host (`vendor=0x10de`, `device=0x2782`). The probe therefore reports `keyed_mutex_result=UNAVAILABLE` and uses event-query synchronization for the passing relay. This agrees with the upstream observation on this machine only; it is not a universal statement about D3D10.1 keyed mutex support.

## Temporal-data constraints

Current ReShade/Feeder evidence shows why D3D10 should not be treated as “almost D3D11”. ReShade effects on the D3D10 path are constrained to Shader Model 4-era capabilities, so motion-vector providers that depend on newer compute/UAV features may not compile or may need pixel-shader alternatives.

DLSS5-Feeder currently treats a legacy D3D10 game as a finished-frame source: no native NGX parameter block, no controlled engine jitter, and estimated ReShade motion vectors. It can therefore exercise a DLAA-style temporal contract, but this is not evidence of real Super Resolution support.

The remaining D3D10 work must separately validate:

- depth access and preservation across clears;
- an SM4-compatible motion provider;
- whether matrices/constants can be intercepted early enough for renderer-derived camera motion and future projection jitter;
- behavior across D3D10.0/10.1 implementations, other GPUs/drivers and a real intercepted executable/game.
